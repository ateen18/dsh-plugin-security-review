# 桌面客户端适配记录（2026-10-21）

本插件最初面向 web 版 dsh（npm 安装的 dsh CLI + 浏览器工作区，运行时 0.1.0-rc.6）。
dsh 桌面客户端把同一套 web 应用打包进 Electron，并用内置的 0.2.1 运行时启动本机宿主。
这篇记录说明两代运行时的差异、改动点，以及桌面端哪些能力不再可用。

## 1. 结论速览

| 能力 | web（0.1.x） | 桌面客户端（0.2.1） | 本插件的处理 |
|---|---|---|---|
| 客户端 UI（设置分区） | `window.__ModuleLoader__.load` | 同一契约 | 不变，只清理了无效的 inject 声明 |
| profile 目录 | 从 `ctx.baseUrl` 推断 | `profileContext.dir` / `installAnchor` | 优先 `profileContext`，退回 `baseUrl` |
| 安装 / 卸载插件 | spawn `dsh plugin add` / `pnpm remove` | `pluginManager.installBundle/removeBundle`；PATH 上没有 dsh/pnpm | 优先 `pluginManager`，其次 desktop CLI，最后 pnpm |
| 设置页 schema | `installSettingsSection` | **已移除** | 特性检测；两代都改用插件自有设置分区 + 持久化文件 |
| install-gate | 改写 `dsh/lib/bin.js` | 运行时在 `app.asar` 内，只读 | 桌面端显式报告 `supported:false, reason:"packaged-runtime"` |
| 导入门禁 / 启动审计 / 工具 | 一样 | 一样 | 不变，补了桌面端的路径解析 |

## 2. 桌面端到底哪里不一样

### 2.1 运行时是打包的、只读的

桌面客户端的 `resources/app.asar/dsh` 是整套 dsh 运行时（包名
`@deepseek-ai/dsh-desktop-runtime`），真正的 dsh 包在
`app.asar/dsh/node_modules/@deepseek-ai/dsh`。因此：

- 不能改写 `lib/bin.js`，install-gate 在桌面端没有落点；
- `findDshInstallRoot()` 若只认 `@deepseek-ai/dsh`，会在 asar 路径上失配——现在同时认
  桌面运行时根，并把「官方包免审判定根」改成运行时根（官方包都在它的 `node_modules` 下）。

### 2.2 没有 PATH 上的 dsh / pnpm

桌面端的包操作统一由启动器注入：

```js
profileContext.packageManager = {
  command: <electron.exe>,
  args: ["--expose-internals", "<runtime>/primary-runtime/dependencies/pnpm/bin/pnpm.mjs"],
  env: { ELECTRON_RUN_AS_NODE: "1", DSH_DESKTOP_NODE_EXECUTABLE: ..., PATH: ... }
}
```

所以插件不能再 `spawn("pnpm")`。现在的顺序是：

1. `ctx.get("pluginManager")` 存在 → `installBundle(spec, {activate:true})` /
   `removeBundle(name)`（自带 profile 写锁、组合包选择、热应用、失败回滚）；
2. 否则用 desktop CLI：`electron --expose-internals <...>/dsh-desktop-host/lib/cli.js plugin --profile <p> add <spec>`；
3. 再否则按 `profileContext.packageManager` 拼 `pnpm add/remove`；
4. 全都没有时给出明确错误，而不是抛异常。

> 注意：`pluginManager` 和本插件在同一批 entry 里启动，`apply` 阶段通常还没就绪。
> 所以取服务必须延迟到调用时（`package-ops.js` 里的 `managerNow()`），不能在 apply
> 时缓存。

### 2.3 设置 API 换了

0.1.x 的 `@deepseek-ai/dsh-settings` 导出 `installSettingsSection`，0.2.1 起没有这个
导出，改成「条目 Config + 宿主设置文档」的模型。本插件的策略不再依赖宿主内部 API：

- 策略持久化在 `$DSH_HOME/security-review/settings.json`（原子写）；
- 设置分区通过 `/api/security-review/settings` 读写，保存后立刻作用到导入门禁与启动审计；
- 若能解析到 0.1.x 的 `installSettingsSection`，仍会额外挂到宿主设置页（web 行为不变）。

### 2.4 0.2.x 的 web server 以 `(kind, path)` 为键

`webServer.register()` 对同一 `(kind, path)` 会抛 `duplicate exact route`。旧代码给
`/api/security-review/gate`、`/settings` 各注册了 GET、POST 两条，在 0.2.x 上第二条直接抛错，
**并让后续所有路由都没注册上**（表现是 gate / capabilities 404）。现在一条路径一个路由，
处理方法分派；注册也改成逐条 try/catch，单条失败不影响其余路由。

### 2.5 模块解析要跟 loader 一致

桌面端 profile 目录下可能同时躺着一份旧版本依赖（例如 0.1.0-rc.6 的
`@deepseek-ai/dsh-*`），而真正被 import 的是 asar 里的 0.2.1 副本。用
`createRequire(profileDir)` 解析会挑到旧副本，版本显示错误、官方包免审也会失效
（193 个内置插件全被当成外部插件）。现在优先用 `ctx.loader.internal.resolveSync()`
（和 host 的 import 走同一条解析链），解析不到才退回 `createRequire`。

## 3. 判定「桌面端」的依据

`lib/desktop.js` 只做只读探测：

- `process.versions.electron` 是否存在；
- dsh 包目录是否位于 `.asar` 内；
- `profileContext.dir` / `installAnchor` 是否存在。

三者任一命中即视为桌面/打包运行时。`/api/security-review/capabilities` 会把结论
（`desktop` / `packaged` / `profileContext` / `packageManager` / `installGate`）返回给设置分区，
界面顶部因此能显示「运行环境：桌面客户端 · 安装通道：plugin-manager」。

## 4. 桌面端仍然可用 / 不再可用

仍然可用：

- 已装插件列表、风险分组、一键审查、报告落盘（`$DSH_HOME/security-review`）；
- 审查 / 安全安装 / 卸载（经 pluginManager，带写锁与热应用）；
- 策略编辑（standard / strict / audit-only、自动禁用、托管拦截、白名单）；
- 会话内工具 `security_review` / `security_review_status`；
- 导入门禁与启动审计（与 web 相同的 loader 补丁）。

不再可用：

- **install-gate**：桌面端没有可写的 `lib/bin.js`，设置分区会直接说明原因，不再假装可用；
- 依赖终端 PATH 的调用（`dsh plugin ...`、`pnpm`）——已由 pluginManager / desktop CLI 替代。

## 5. 验证方式

1. `node --test "test/*.test.mjs"`：66 项通过（含新增 `test/desktop.test.mjs` 的 21 项：
   profileContext 优先级、asar 识别、install-gate 能力、桌面运行时布局、策略持久化、
   pluginManager 安装/卸载折叠、路由表唯一性 / 方法分派 / 回环限制、客户端 bundle 契约）。
2. 用桌面运行时的 CLI 起一个临时 profile（`sr-smoke`），装本插件后实测：
   - `/api/security-review/{list,settings,capabilities,gate,run}` 全部返回 200；
   - `capabilities` 报告 `desktop:true, packaged:true, pluginManager:true, installGate.supported:false`；
   - `list` 的 193 个条目中 192 个被正确识别为官方（`official:true`，版本 0.2.1-rc.2）；
   - 安装夹具插件时走 `pluginManager.installBundle`，pnpm 正常执行；因为夹具没有
     `dsh.bundle.patch`，管理器按规则回滚并报 `not-bundle`（这是预期行为，文案已翻译）；
   - 首页 `__DSH_BOOT__` 里包含 `dsh-plugin-security-review/client.js`，combo bundle
     能被取到并包含 `__ModuleLoader__.load({id:"dsh-plugin-security-review"})`。

## 6. 已知限制

- 只在 Windows 上的桌面客户端验证过；`lib/desktop.js` 的判断是平台无关的，但 macOS/Linux 的
  打包布局（`Contents/Resources/app.asar`）与 CLI 包装脚本没有实测。
- 桌面端的 install-gate 永久不可用；要拦住 `dsh plugin add`，只能靠插件内的「安全安装」或
  `dsh-safe-plugin` CLI。
- 0.2.x 只允许安装声明了 `dsh.bundle.patch` 的包；普通 npm 包装进去会被回滚（提示 `not-bundle`）。
- 策略文件是插件自己的，不走宿主设置文档；重装/换机会保留在 `$DSH_HOME/security-review/settings.json`。
