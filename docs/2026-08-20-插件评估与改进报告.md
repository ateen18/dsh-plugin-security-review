# 安全审查插件评估与改进报告

日期：2026-08-20
对象：`dsh-plugin-security-review` v0.1.0（约 2700 行，零运行时依赖）

## 一、插件定位与架构评估

本插件为 dsh（DeepSeek Harness）提供插件供应链安全门禁，采用三层防御：

| 层级 | 机制 | 位置 |
|------|------|------|
| 安装门禁 | CLI 预审查（`dsh-safe-plugin add`，自动附加 `--ignore-scripts`） | `lib/cli/index.js` |
| 运行时门禁 | patch `EntryTree.prototype.import` 拦截 + 启动审计 | `lib/gate.js` |
| 会话内工具 | agent 可调用的审查/放行工具 | `lib/tools.js` |

**架构优点：**

1. **零依赖纯静态分析**——不执行被审查代码，18 组规则全部基于正则与轻量语法启发式，攻击面小、启动开销低。
2. **host.js 的模块实例共享设计正确**——从 dsh 安装根解析 `@deepseek-ai/*` 宿主包，避免双实例导致的 instanceof/上下文割裂（这是 2026-08-18 修复的启动崩溃根因，见 `docs/2026-08-18-启动崩溃问题修复报告.md`）。
3. **拒收式 tar 解包**——路径穿越拒绝、符号链接记录、escape 警告，符合供应链扫描的最低安全要求。
4. **managed block 行级编辑**——只重写标记之间的内容，保留用户其余 patch 配置。

## 二、本轮修复的问题（dsh 启动失败根因链）

用户报告"安装插件后 dsh 总是启动失败"。排查发现是**三重 bug 叠加**：

### 根因 1：tar 解包完全失效（`lib/analyzer/tar.js`）

`Buffer.toString(encoding, start, end)` 第三参数是**结束偏移**而非长度。原代码 `header.toString("utf8", 257, 6)` 返回空串，导致 ustar magic 校验永远失败，registry 包审查全军覆没。

### 根因 2：`danger-child-process` 规则大面积误报（`lib/analyzer/rules.js`）

- 旧正则把 `RegExp.prototype.exec()` 当作 `child_process.exec()`；
- 240 字符窗口内出现**任意**反引号即判 critical（连 `shell: false` 显式声明也压不住）；
- 结果：`dshmarket`、`@linxin666/dsh-remote-web-ui`、`dsh-ssh`、`dsh-client-ui-aionui-panel` 四个合法社区插件被判 block，运行时门禁把 `disabled: true` 写进 profile → dsh 依赖这些插件的服务/UI → 启动失败。

**修复**：规则重写为「先收集真实的 child_process 绑定名，只对实际调用点判定」；severe 判定拆为 120 字符参数窗口（模板插值）+ 240 字符选项窗口（shell 选项），`shell: false` 显式降级，`shell: <表达式>` 视为可疑。

### 根因 3：清空 managed block 后 profile 文件变成非法 YAML（`lib/patch-manager.js`）

block 清空后 `cordis.patch.yml` 只剩注释，YAML 解析为 `null`，dsh 启动直接抛 `must be a top-level YAML array`。**这是本轮最后发现的隐藏炸弹**——即使规则误报修好，只要曾经禁用过再放行，dsh 依然起不来。

**修复**：`sync()` 输出前检测有效内容行，为空时补 `[]` 占位。

### 配套修复

| 文件 | 修复 |
|------|------|
| `rules.js` | `SENSITIVE_ENV` 不再匹配任意 `process.env`；localStorage→网络需有实际数据流才升 high；`prepare: npm run build` 降级 low；schemastery 式 `new Function` 降 high；`atob` 未流入 eval 不判混淆 |
| `score.js` | 评分按规则 ID 去重（16 处 spawn 调用点 ≠ 危险 16 倍）；删除 `score<30→block`（累计扣分误杀合法插件），block 只由 critical 或 strict+high 触发 |
| `files.js` | 默认忽略 `test/`、`fixtures/`、`*.test.js` 等（可 `defaultIgnore:false` 关闭）——自审查不再被自己的恶意样本夹具炸出 critical |

### 修复后验证结果

- 测试套件 **19/19 通过**（含新增回归测试：tar 解包、误报、误禁插件、自审查、patch-manager）
- 四个曾误禁插件复审：`dshmarket` warn/51、`dsh-remote-web-ui` pass/81、`dsh-ssh` warn/50、`aionui-panel` pass/77
- 插件自审查：**warn/70**（修复前 block/28）
- `dsh --profile web --dump-config` 组合成功，4 个插件全部恢复启用
- 真实启动测试：插件树完整加载（仅在 3080 端口因用户已有实例运行而冲突，与插件无关）

## 三、效果评估

### 能力（当前可拦截的真实威胁）

- 安装脚本执行、注册表完整性校验失败（sha512 不符）、tar 路径穿越
- shell:true + 用户输入插值的命令注入、eval/Function 动态执行
- 凭据读取 + 网络外传同文件共存、硬编码 webhook/API key
- typosquat 近似名检测（`dsh-pet` vs `dsh-pets`）
- 混淆特征（atob→eval 数据流）、可疑依赖名

### 局限（静态分析的固有边界）

1. **无污点追踪**——"用户输入是否真到达 exec()"只能靠窗口启发式，既可能漏报（输入经 3 层函数传递后拼接）也可能误报。
2. **无控制流/作用域感知**——`if (false) { exec(...) }` 照样报。
3. **规则可被绕过**——`globalThis["child_" + "process"]`、`process["mainModule"]` 等动态属性访问不在规则覆盖内；minified 代码中变量名收集会失效。
4. **评分是启发式聚合**——70 vs 51 的差距语义弱，不宜作为唯一决策依据（好在 block 逻辑已改为只看具体高危信号）。

## 四、改进建议（按优先级）

### P0（建议尽快做）

1. **误禁自愈**：启动审计发现某插件 verdict 从 block 变为非 block 时，自动从 managed block 移除（当前需手动 `dsh-safe-plugin` 操作；本次事故中 4 个插件就是靠手动清理恢复的）。
2. **gate 拦截降级选项**：运行时门禁默认对"已有配置在 profile 中、但复审仅 warn"的包放行并告警，避免规则迭代导致已装用户被锁死。
3. **patch-manager 写后校验**：写文件后用 YAML 解析验证（或至少检测非注释内容行），失败即回滚——本次根因 3 这类"写坏配置文件"的错误必须在写入时拦截。

### P1（显著提升能力）

4. **轻量 AST**：引入 `acorn`（约 120KB、单文件、零依赖）做 AST 级调用点识别，替代正则绑定名收集，消除 minified/动态成员访问的盲区；正则规则保留做快速预筛。
5. **报告缓存**：以 spec+version+integrity 为键缓存审查报告，启动审计每次全量重扫 4 个插件约 2-3 秒，缓存后可降到毫秒级。
6. **理由披露**：block 时在 reason 中给出可复现的 `dsh-safe-plugin review <spec>` 命令与具体 finding 位置，降低排查成本。

### P2（长期方向）

7. **与 npm registry 元数据联动**：发布时间 <7 天、无 README、单发布者全量包名等 supply-chain 信号目前只有 `weak-metadata` 一条规则，可扩展为打分维度。
8. **会话内审查工具的 prompt 集成**：让 agent 在"用户要求装插件"时主动走 CLI 门禁而非直接 pnpm add。
9. **lockfile 审计**：对 profile `node_modules` 的依赖树做 lockfile 级比对，发现未审查的间接依赖。

## 六、结论

插件的三层防御架构合理、零依赖静态分析在 dsh 场景下是正确的取舍；但 v0.1.0 的规则引擎误报率足以造成**"安全工具自身把宿主搞挂"**的反效果。本轮修复后误报问题基本收敛（4 个误禁插件全部恢复、自审查 warn/70），三层 bug（tar 偏移、正则误报、YAML 写坏）均有回归测试覆盖。下一步优先落实 P0 的三项自愈/校验机制，把"门禁出错时的爆炸半径"从"dsh 起不来"降到"一条告警日志"。
